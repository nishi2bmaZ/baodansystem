## 一、项目概述

### 1.1 项目背景

公司自有的**星际未来平台**已沉淀了一批会员，并具备完整的**推荐关系树**（以邮箱账号为唯一标识）。这些会员需要前往一个**外部商城平台**完成日常任务。

问题在于：外部商城以**手机号**作为账号标识，且不承载任何推荐关系。这导致两侧数据完全割裂——商城只知道"谁做了任务"，却不知道"这个人属于哪条推荐线"；星际未来知道推荐关系，却拿不到商城侧的任务完成数据。

因此需要建设一套**中间层报单系统**，把两个平台的身份打通，承载任务分发、任务提交、人工审核与对账导出的完整闭环。

### 1.2 业务现状与核心痛点

| 编号 | 痛点 | 现状描述 | 造成的影响 |
| --- | --- | --- | --- |
| P1 | 身份割裂 | 星际未来用邮箱，商城用手机号，无映射关系 | 无法归因，业绩统计断层 |
| P2 | 推荐关系缺失 | 商城侧完全没有推荐关系概念 | 团队业绩无法核算，激励机制无法落地 |
| P3 | 任务分发靠人工 | 任务通过群通知，先到先做，容易超量 | 名额失控，超出预算 |
| P4 | 提交材料混乱 | 截图发在群里或私聊，散落各处 | 审核效率低，材料易丢失 |
| P5 | 审核无系统 | 人工肉眼比对，无留痕、无统计 | 审核标准不统一，纠纷难追溯 |
| P6 | 对账困难 | 与商城核对需手工整理表格 | 耗时长，易出错 |
| P7 | 防重复能力弱 | 同一截图可能被重复提交 | 存在结算风险 |

### 1.3 项目目标

**业务目标**

- 建立星际未来邮箱 ↔ 商城手机号的**一对一可信映射**
- 通过人工干预方式，在报单系统内**重建完整推荐关系树**，并可参照星际未来后台随时校正
- 任务全流程线上化：**发布 → 抢名额 → 做任务 → 提交材料 → 审核 → 导出对账**
- 审核结果一键导出，与商城对账时间从"数小时"压缩到"分钟级"

**技术目标**

- 任务表单**完全后台可配置**，新增任务类型无需发版
- 名额抢占在高并发下**零超发**
- 系统支撑 **5000+ 注册会员、单场次 2000 人同时抢单**
- 图片材料统一存储，支持跨用户、跨日期的**自动查重**

**量化指标（上线三个月内验收）**

| 指标 | 目标值 |
| --- | --- |
| 抢单接口 P99 响应时间 | ≤ 300ms |
| 名额超发率 | 0% |
| 审核单条平均耗时 | ≤ 15 秒 |
| 对账导出耗时（万级数据） | ≤ 30 秒 |
| 系统可用性 | ≥ 99.5% |
| 重复截图检出率 | ≥ 95% |

### 1.5 项目范围

**本期包含（In Scope）**

- 会员端 H5：注册、登录、任务大厅、抢单、提交、进度查询、我的团队
- 管理后台：会员管理、推荐关系管理、任务模板配置、场次发布、审核工作台、导出、风控、系统设置

**本期不包含（Out of Scope）**

- 佣金结算、提现、资金流转（列入二期，本期仅做数据沉淀）
- App 原生客户端（本期为 H5，可套壳）
- 多语言、多币种

### 1.6 关键设计假设

> 以下假设需业务方确认，如有出入将影响方案设计。

| 编号 | 假设 | 影响面 |
| --- | --- | --- |
| A1 | 一个星际未来邮箱只能绑定一个商城手机号，反之亦然 | 注册校验逻辑、防作弊 |
| A2 | 星际未来的推荐关系可导出为 Excel（含邮箱、上级邮箱） | 推荐关系初始化方式 |

### 3.2 注册与账号绑定流程

```
开始
 ↓
填写星际未来邮箱 ──> 格式校验 ──> 是否已被注册？──是──> 提示"该邮箱已注册" ──> 结束
 ↓ 否
填写商城手机号 ──> 格式校验 ──> 是否已被绑定？──是──> 提示"该手机号已绑定其他账号" ──> 结束
 ↓ 否
[可选] 短信验证码校验手机号真实性
 ↓
填写推荐人邮箱（选填）──> 校验该邮箱是否存在
 ↓
设置登录密码 + 确认密码 ──> 强度校验（8位以上，含字母数字）
 ↓
勾选服务协议
 ↓
提交注册
 ↓
系统创建账号，状态 = 待审核（可配置为直接生效）
 ↓
若填写了推荐人 ──> 自动建立推荐关系（来源标记 = 注册填写）
若未填写 ──> 挂入"待分配"池，等待关系管理员人工指定
 ↓
后台审核通过 ──> 账号生效，可登录抢单
 ↓
结束
```

**关键规则**

- 邮箱与手机号均为**全局唯一**，数据库层面加唯一索引兜底
- 密码使用 **bcrypt**（cost=10）加盐哈希存储，禁止明文或可逆加密
- 注册是否需要人工审核，由后台开关控制（默认开启，防止批量注册）
- 手机号短信验证为可选项，由后台开关控制（考虑短信成本）
- 注册时可强制要求填写推荐人邮箱，由后台开关控制

### 3.4 名额与超时释放机制

名额是本系统最核心的稀缺资源，必须保证**不超发、不浪费**。

```
总名额 100
   │
   ├── 已抢占未提交（CLAIMED）    占用中，倒计时进行
   │        │
   │        ├── 按时提交 ──> 转为 PENDING（仍占用名额）
   │        ├── 超时未提交 ──> EXPIRED，名额回补 +1
   │        └── 主动放弃 ──> CANCELLED，名额回补 +1
   │
   ├── 待审核（PENDING）          占用中
   │        ├── 审核通过 ──> APPROVED（永久占用）
   │        └── 审核驳回 ──> REJECTED
   │                 ├── 允许重提 ──> 仍占用名额，等待会员修改
   │                 └── 不允许重提 ──> 名额回补 +1（可配置）
   │
   └── 剩余可抢名额 = 总名额 - 占用中数量
```

**释放策略配置项**

| 配置项 | 说明 | 默认值 |
| --- | --- | --- |
| 占位有效期 | 抢单后多久内必须提交 | 60 分钟 |
| 超时是否释放 | 超时后名额是否回补给他人 | 是 |
| 驳回是否释放 | 审核驳回后名额是否回补 | 否（允许重提） |
| 允许主动放弃 | 会员可否主动取消已抢名额 | 是 |
| 放弃惩罚 | 当日放弃超过 N 次后禁止再抢 | 3 次 |
| 场次结束后处理 | 截止时间到达时未提交的记录如何处理 | 全部置为 EXPIRED |

**技术实现**：采用 Redis 延迟队列（或 BullMQ delayed job）+ 定时兜底扫描双重保障。延迟任务在抢单成功时投递，到期检查状态；定时任务每分钟扫描一次，捕获延迟队列丢失的漏网记录。

### 3.5 推荐关系建立与调整流程

由于商城侧没有推荐关系，报单系统需要以**星际未来邮箱**为桥梁重建关系树。系统提供三种建立方式：

**方式一：注册时自主填写（覆盖率约 60-70%）**

会员注册时填写推荐人的星际未来邮箱，系统校验该邮箱存在后自动建立父子关系，标记来源为 `SELF_INPUT`。

**方式二：Excel 批量导入（推荐，覆盖率最高）**

```
星际未来后台导出推荐关系表
 ↓
Excel 格式：会员邮箱 | 上级邮箱 | 会员昵称 | 注册时间
 ↓
关系管理员上传至报单系统
 ↓
系统解析并逐行校验
 ├─ 会员邮箱在报单系统不存在 ──> 记录到"未注册名单"，跳过
 ├─ 上级邮箱不存在 ──> 记录异常，标记待处理
 ├─ 会检测环路（A→B→C→A）──> 拒绝该行并报错
 └─ 校验通过 ──> 加入待确认列表
 ↓
展示预览：新增 X 条、变更 Y 条、冲突 Z 条
 ↓
管理员确认 ──> 事务提交，全量重算 path 与 depth
 ↓
生成变更日志（谁、何时、从哪个上级改到哪个上级）
```

**方式三：后台单条人工调整**

关系管理员在会员详情页直接修改上级，用于处理个案纠纷或新增会员。

**调整时的子树迁移逻辑**

当把会员 B 从上级 A 迁移到上级 C 时：

1. 校验 C 不在 B 的子树内（防止形成环路）
2. 更新 B 的 `parent_id = C`、`depth = C.depth + 1`
3. 计算路径前缀差值，批量更新 B 及其所有后代的 `path` 与 `depth`
4. 整个过程在**单个数据库事务**内完成
5. 写入 `referral_change_log`，记录操作人、时间、变更前后、原因

```sql
-- 子树路径批量更新示例（PostgreSQL）
UPDATE members
SET path = :new_prefix || SUBSTRING(path FROM LENGTH(:old_prefix) + 1),
    depth = depth + :depth_delta
WHERE path LIKE :old_prefix || '%';
```

#### 4.2.6 审核工作台

**设计目标**：让审核员用最少的点击完成最多的审核，单条平均耗时控制在 15 秒内。

**列表模式**

- 筛选：任务、日期范围、状态、会员邮箱/手机号、订单号、推荐线、审核员、风险标记
- 排序：提交时间正序（先提交先审）/ 倒序 / 风险等级
- 列表展示关键字段 + 图片缩略图，鼠标悬停放大
- 支持**批量通过**（勾选多条 → 一键通过）
- 支持**批量驳回**（勾选多条 → 选择统一原因）

**逐条审核模式（推荐主力模式）**

```
┌───────────────────────────────────────────────┐
│  待审核 128 条        当前第 1 条    [跳过] [↑][↓] │
├─────────────────────────┬─────────────────────┤
│                         │  会员：abc@mail.com   │
│                         │  手机：138****8888    │
│      [ 提交的截图 ]      │  上级：xyz@mail.com   │
│      支持缩放/旋转       │  任务：XX商城下单任务  │
│      多图左右切换        │  订单号：2026081012.. │
│                         │  金额：￥128.00       │
│                         │  提交时间：14:23:11   │
│                         │  ─────────────────   │
│                         │  ⚠ 风险提示：         │
│                         │  该图片与报单#8821相似 │
├─────────────────────────┴─────────────────────┤
│  [ ✓ 通过 (A) ]   [ ✗ 驳回 (D) ]   [ 标记可疑 ]  │
└───────────────────────────────────────────────┘
```

**效率优化**

- **键盘快捷键**：A = 通过，D = 驳回，← → = 上一条/下一条，1-9 = 快速选择驳回原因
- 通过后**自动跳转下一条**，无需返回列表
- 图片**预加载**下一条，消除等待
- 驳回原因支持**预设模板**（截图不清晰、订单号不符、金额不符、非本人账号、重复提交、订单已取消、其他）
- 审核完成后显示本次审核统计（共审 X 条，通过 Y，驳回 Z，耗时 N 分钟）

**审核规则**

- 同一条报单**同时只能被一名审核员锁定**（Redis 分布式锁，防止重复审核）
- 锁定超时 5 分钟自动释放
- 审核记录不可删除，只能追加"撤销审核"操作（需超管权限，全程留痕）
- 支持配置**双审模式**（初审 + 复审），针对高金额任务

### 5.4 关键设计决策

**决策一：JSONB 存储 + 关键字段抽取**

表单数据整体以 JSONB 存入 `submissions.form_data`，保证结构灵活。同时通过 Schema 中的 `extractFields` 声明关键字段，提交时自动抽取到独立物理列（`extract_order_no`、`extract_amount`），用于建索引、做唯一校验、支撑高性能查询与导出。

> 这是灵活性与查询性能的平衡点。纯 JSONB 查询在数据量大时性能不佳，纯物理列则丧失灵活性。

**决策二：模板版本化**

每次发布模板生成新版本号，`submissions` 记录 `template_version`。渲染历史报单时按当时的版本 Schema 渲染，保证旧数据永远显示正确。

**决策三：三层校验**

| 层级 | 位置 | 职责 |
| --- | --- | --- |
| 第一层 | 前端 | 即时反馈，提升体验（可被绕过，不可信） |
| 第二层 | 后端 | 依据 Schema 重新执行全部校验（权威校验） |
| 第三层 | 数据库 | 唯一索引、非空、外键（最终兜底） |

后端校验必须**独立于前端**完整实现一遍，绝不能因为前端校验过了就跳过。

**决策四：字段变更约束**

| 操作 | 已有报单数据时 | 说明 |
| --- | --- | --- |
| 新增字段 | ✅ 允许 | 老数据该字段为空 |
| 修改字段标题/提示 | ✅ 允许 | 不影响数据 |
| 修改字段类型 | ❌ 禁止 | 会导致老数据无法解析 |
| 删除字段 | ❌ 禁止 | 改为"停用"，历史数据仍可查看 |
| 修改 key | ❌ 禁止 | 数据键名断裂 |
| 放宽校验规则 | ✅ 允许 | — |
| 收紧校验规则 | ⚠️ 警告 | 仅对新提交生效，需二次确认 |

## 六、名额与并发控制设计

### 6.1 问题描述

抢单是典型的**秒杀场景**：2000 人在同一秒争抢 100 个名额。必须解决三个问题：

1. **超发**：卖出 105 个名额，多出的 5 个无法结算
2. **少发**：明明有名额却提示抢完，浪费资源、引发投诉
3. **重复占用**：网络抖动导致用户重复点击，一人占多个名额

### 6.2 技术方案：Redis 原子扣减 + 数据库唯一索引双保险

```
用户点击抢单
      ↓
① 幂等校验（Redis SETNX idempotency:{token}，TTL 5min）
   命中 ──> 直接返回首次结果
      ↓ 未命中
② 前置校验（本地缓存 + Redis）
   · 场次是否在有效时间内
   · 用户状态是否正常、是否在黑名单
   · 用户在本场次已抢数量是否超限（Redis Hash 计数）
      ↓ 通过
③ Lua 脚本原子执行（保证操作不可分割）
   KEYS: quota:{instanceId}, user_count:{instanceId}:{userId}
   逻辑：
     if 剩余名额 <= 0 then return -1 end
     if 用户已抢数 >= 单人上限 then return -2 end
     DECR 剩余名额
     HINCRBY 用户已抢数 +1
     return 剩余名额
      ↓ 返回 >= 0
④ 写入数据库（事务）
   INSERT INTO submissions (..., status='CLAIMED', claim_seq=N)
   唯一索引：uk_instance_user_seq (instance_id, member_id, claim_seq)
   ├─ 插入失败（唯一冲突）──> 回滚 Redis 计数，返回"请勿重复操作"
   └─ 插入成功
      ↓
⑤ 投递延迟任务（占位超时检查，delay = 占位有效期）
      ↓
⑥ 返回成功 + 提交截止时间戳
```

**Redis 数据结构**

| Key | 类型 | 说明 |
| --- | --- | --- |
| `trs:quota:{instanceId}` | String | 剩余名额计数器 |
| `trs:user_claim:{instanceId}` | Hash | field=memberId, value=已抢数量 |
| `trs:idem:{token}` | String | 幂等令牌，TTL 5 分钟 |
| `trs:lock:review:{submissionId}` | String | 审核锁，TTL 5 分钟 |

**缓存预热与一致性**

- 场次开始前 10 分钟由定时任务预热 Redis 名额计数
- 每 30 秒由后台任务用数据库真实占用数**校准** Redis 计数（只在差异超过阈值时修正，并告警）
- Redis 故障降级：切换为数据库悲观锁模式（`SELECT ... FOR UPDATE`），性能下降但保证正确性

### 6.3 报单状态机

```
                    ┌──────────────┐
                    │   CLAIMED    │ 已抢占（占用名额，倒计时中）
                    └──────┬───────┘
           ┌───────────────┼───────────────┐
           │               │               │
      提交表单         超时未提交       主动放弃
           ↓               ↓               ↓
    ┌────────────┐  ┌────────────┐  ┌─────────────┐
    │  PENDING   │  │  EXPIRED   │  │  CANCELLED  │
    │  待审核     │  │  已过期     │  │  已取消      │
    └─────┬──────┘  │ (名额回补)  │  │ (名额回补)   │
          │         └────────────┘  └─────────────┘
    ┌─────┴─────┐
    │           │
  通过        驳回
    ↓           ↓
┌─────────┐ ┌──────────┐
│APPROVED │ │ REJECTED │
│ 已通过   │ │  已驳回   │
└─────────┘ └────┬─────┘
                 │ 允许重提且未超次数
                 ↓
            回到 PENDING
```

**状态流转约束**

- 所有状态变更走统一的状态机服务，禁止业务代码直接 UPDATE status
- 每次变更写入 `submission_status_log`（原状态、新状态、操作人、原因、时间）
- 终态：`APPROVED`、`EXPIRED`、`CANCELLED`、`REJECTED`（不允许重提时）
- 状态变更使用**乐观锁**（version 字段），防止并发覆盖

### 6.4 超时释放实现

**双重保障机制**

- **主机制**：BullMQ 延迟任务。抢单成功时投递 `delay = 占位有效期` 的任务，到期时检查该报单状态，若仍为 `CLAIMED` 则置为 `EXPIRED` 并回补 Redis 与数据库名额
- **兜底机制**：定时任务每分钟扫描 `status='CLAIMED' AND expire_at < NOW()` 的记录批量处理，捕获延迟队列丢失的漏网记录
- **释放动作原子性**：先用乐观锁更新数据库状态（`WHERE status='CLAIMED'`），更新成功（影响行数=1）才回补 Redis，避免重复回补

## 七、推荐关系设计

### 7.1 数据模型选型

树形结构常见方案对比：

| 方案 | 查询整棵子树 | 查询祖先链 | 迁移节点 | 结论 |
| --- | --- | --- | --- | --- |
| 邻接表（仅 parent_id） | 递归，慢 | 递归，慢 | 极快 | ❌ 查询性能差 |
| 闭包表 | 快 | 快 | 需重建大量行 | ⚠️ 存储膨胀 |
| **物化路径（推荐）** | **快（前缀 LIKE）** | **快（解析 path）** | **中等（前缀替换）** | ✅ **采用** |
| 嵌套集 | 极快 | 快 | 极慢 | ❌ 频繁调整不适用 |

**结论：采用物化路径（Materialized Path），同时保留 `parent_id` 字段便于直接查询直推。**

```
会员 A (id=1)   path = "/1/"          depth = 0
├─ 会员 B (id=5) path = "/1/5/"       depth = 1
│   ├─ 会员 D (id=9)  path = "/1/5/9/"  depth = 2
│   └─ 会员 E (id=12) path = "/1/5/12/" depth = 2
└─ 会员 C (id=7) path = "/1/7/"       depth = 1
```

**典型查询**

```sql
-- 查询 B 的整个团队（所有层级下级）
SELECT * FROM members WHERE path LIKE '/1/5/%' AND id <> 5;

-- 查询 B 的直推
SELECT * FROM members WHERE parent_id = 5;

-- 查询 D 的所有上级链
SELECT * FROM members WHERE id IN (1, 5);  -- 由 path 解析得出

-- 统计 B 的团队今日报单数
SELECT COUNT(*) FROM submissions s
JOIN members m ON s.member_id = m.id
WHERE m.path LIKE '/1/5/%' AND s.created_at::date = CURRENT_DATE;
```

### 7.2 环路检测

在任何关系变更前必须检测环路，否则会导致 path 计算无限递归。

```
校验规则：新上级 C 不能是被调整会员 B 的后代
判定方法：检查 C.path 是否以 B.path 为前缀
  若 C.path LIKE B.path || '%' 则形成环路，拒绝操作
```

批量导入时需构建完整的有向图，用**拓扑排序或 DFS 着色法**全量检测环路，任何一条形成环路即整批拒绝并给出明确定位。

### 7.3 关系变更的影响评估

调整关系前，系统需向管理员展示影响面：

```
┌────────────────────────────────────────┐
│  关系调整确认                            │
├────────────────────────────────────────┤
│  会员：zhangsan@mail.com                │
│  原上级：old_leader@mail.com            │
│  新上级：new_leader@mail.com            │
│                                        │
│  ⚠ 本次调整将影响：                      │
│    · 该会员及其 23 名下级的归属关系       │
│    · old_leader 团队人数：156 → 132     │
│    · new_leader 团队人数：89 → 113      │
│    · 涉及历史报单 1,847 条的归属统计      │
│                                        │
│  调整原因（必填）：                       │
│  [________________________________]     │
│                                        │
│         [ 取消 ]      [ 确认调整 ]       │
└────────────────────────────────────────┘
```

**历史数据处理策略**：报单表中冗余存储提交当时的 `parent_id_snapshot` 和 `path_snapshot`。这样关系调整**不会篡改历史业绩归属**，同时支持按"当前关系"和"历史关系"两种口径出报表。这一点必须在开发前与业务方确认口径。

### 8.3 索引与性能要点

| 场景 | 优化手段 |
| --- | --- |
| 订单号防重 | 唯一部分索引（排除已取消记录） |
| 团队查询 | `path` 使用 `varchar_pattern_ops`，前缀 LIKE 走索引 |
| 超时扫描 | 部分索引 `WHERE status='CLAIMED'`，仅索引待处理数据 |
| 审核列表 | 复合索引 `(status, created_at DESC)` |
| 大数据量导出 | 游标分页（Keyset Pagination），避免深度 OFFSET |
| 历史数据 | 报单表按月分区（数据量超 500 万后启用） |
| 统计报表 | 每日凌晨物化视图刷新，避免实时聚合 |

| 环境 | 用途 | 配置建议 |

**容量估算（5000 会员，日均 3000 报单）**

| 资源 | 估算 |
| --- | --- |
| 数据库年增数据量 | 报单约 110 万条，约 3-5 GB |

### 10.4 文件上传方案

```
前端选择图片
   ↓
前端压缩（canvas，长边 ≤1920，quality 0.8）
   ↓
计算文件 MD5（前端 SparkMD5 分片计算）
   ↓
请求后端：POST /upload/token { md5, fileName, size, fieldKey }
   ↓
后端校验：
  · 文件大小、类型是否合规
  · MD5 是否已存在（秒传：已存在则直接返回已有 URL；同时记录疑似重复）
   ↓
返回 COS 临时凭证（STS，5 分钟有效，限定路径前缀）
   ↓
前端直传 COS（带进度条，失败自动重试 3 次）
   ↓
上传成功后回调后端：POST /upload/callback
   ↓
后端异步任务：生成缩略图、计算 pHash、写入 submission_files
```

**存储路径规范**：`trs/{yyyy}/{MM}/{dd}/{memberId}/{uuid}.{ext}`

**安全**：COS 存储桶设为**私有读**，访问时由后端签发带时效的临时 URL（有效期 10 分钟），防止图片外链泄露与盗刷流量。

### 10.5 安全设计

| 类别 | 措施 |
| --- | --- |
| 传输 | 全站 HTTPS，HSTS，TLS 1.2+ |
| 密码 | bcrypt(cost=10) 加盐哈希，禁止明文/MD5 |
| 认证 | JWT 双 Token；Refresh Token 存 Redis 可主动吊销 |
| 越权 | 所有资源访问校验归属（会员只能操作自己的报单）；后台接口逐个校验权限点 |
| 注入 | 全部使用参数化查询/ORM，禁止字符串拼接 SQL |
| XSS | 富文本使用 DOMPurify 白名单过滤；输出转义 |
| CSRF | JWT + 自定义 Header，不依赖 Cookie |
| 上传 | 校验 MIME + 文件头魔数（不只看扩展名）；图片重编码剥离恶意载荷；禁止上传可执行文件 |
| 限流 | 按 IP + 用户维度限流；抢单接口单用户 1 秒 1 次；短信 60 秒 1 条、每日上限 10 条 |
| 敏感数据 | 手机号/邮箱在列表页脱敏展示；导出行为全量记录审计日志 |
| 后台 | 强制强密码 + 建议开启 TOTP 二次验证；可配置 IP 白名单 |
| 防爆破 | 登录失败 5 次锁定 30 分钟；图形验证码/滑块 |
| 备份 | 数据库每日全量 + 实时 WAL 归档，保留 30 天，每季度演练恢复 |

## 十二、风控与防作弊

### 12.1 风险场景与对策

| 风险场景 | 危害 | 对策 |
| --- | --- | --- |
| 同一截图重复提交 | 重复结算，资金损失 | MD5 精确查重 + pHash 相似查重，跨用户跨日期比对 |
| PS 伪造截图 | 虚假报单 | 人工审核 + 高清原图查看 + 图片 EXIF 检查 + 抽检机制 |
| 一人注册多账号 | 刷取名额 | 邮箱唯一 + 手机号唯一 + 设备指纹 + IP 聚集告警 |
| 脚本抢单 | 破坏公平性 | 抢单接口人机校验、限流、幂等、行为特征分析 |
| 抢单不做单 | 浪费名额 | 占位有效期 + 超时释放 + 放弃次数惩罚 |
| 订单号编造 | 无法对账 | 订单号格式校验 + 全局唯一 + 与商城对账清单反向核验 |
| 内部人员舞弊 | 违规放行 | 审核操作全量留痕 + 审核员通过率异常监控 + 抽检复核 |
| 数据导出泄露 | 用户信息泄露 | 导出权限最小化 + 导出记录审计 + 敏感字段脱敏可选 |

### 12.2 图片查重算法

```
提交图片
   ↓
① MD5 精确匹配
   在 submission_files 中查找相同 MD5
   命中 ──> 高危，直接拦截或强制人工复核
   ↓ 未命中
② 感知哈希 pHash（64 位）
   计算流程：缩放 32×32 → 灰度化 → DCT 变换 → 取低频 8×8 → 均值二值化
   ↓
③ 汉明距离比对
   与近 N 天（默认 30 天）同任务的图片比对
   距离 ≤ 5  ──> 高度相似，标记高危
   距离 6-10 ──> 疑似相似，标记待复核
   距离 > 10 ──> 通过
   ↓
④ 命中则写入 risk_alerts，审核界面醒目提示并展示对比图
```

**性能优化**：pHash 计算放入异步队列，不阻塞提交流程；比对范围通过任务 ID + 时间窗口收敛；数据量大时可引入 BK-Tree 或将哈希分段建索引加速。

### 12.3 业务合规提示

> 本节需业务负责人重点关注。

系统本身是中性的任务管理工具，但**任务内容的合规性决定了整个项目的法律风险**。建议：

1. 确保任务为真实的商品体验、推广或内容创作行为，**避免涉及虚假交易、刷单炒信**——《反不正当竞争法》第八条明确禁止虚假交易，平台方与参与者均可能承担责任
2. 在会员注册协议与任务说明中明确任务规则、禁止行为与违规处理条款
3. 保留完整的任务发布记录、提交材料与审核记录，作为合规举证材料
4. 会员个人信息（邮箱、手机号）的收集需符合《个人信息保护法》：明示收集目的、取得同意、最小必要、保障安全
5. 建议上线前由法务对任务模式与用户协议出具意见

### 13.2 交互设计要点

**会员端**

- 目标用户可能对手机操作不熟练，界面必须**大字号、大按钮、少层级**
- 关键操作（抢单、提交）按钮固定在屏幕底部，拇指易达
- 状态用**颜色 + 文字**双重表达，不依赖颜色单一维度（考虑色弱用户）
  - 待提交 = 橙色｜待审核 = 蓝色｜已通过 = 绿色｜已驳回 = 红色｜已过期 = 灰色
- 所有耗时操作必须有 loading 态与防重复点击
- 错误提示必须**明确告知原因和下一步怎么做**，禁止"操作失败"这类无效文案
- 倒计时全部基于服务器时间，页面重新激活（visibilitychange）时重新校准
- 表单支持草稿保存，退出时二次确认

**管理后台**

- 审核工作台为**高频重复操作**场景，必须支持键盘快捷键与自动跳转下一条
- 列表页筛选条件支持保存为"我的常用筛选"
- 所有批量操作前显示影响条数并二次确认
- 危险操作（删除、禁用、关系调整）二次确认且要求填写原因
- 表格支持列显示配置、列宽拖拽、密度切换，并记忆用户偏好

### 15.2 关键测试用例

**名额并发（最高优先级）**

| 用例 | 预期结果 |
| --- | --- |
| 100 名额，1000 人同时抢 | 恰好 100 人成功，`used_quota = 100`，无超发 |
| 同一用户快速点击 10 次（相同幂等 Token） | 仅占用 1 个名额，返回相同结果 |
| 单人限额 2，用户尝试抢 5 次 | 前 2 次成功，后 3 次返回 USER_LIMIT_EXCEEDED |
| 抢单后超时未提交 | 到期自动 EXPIRED，名额回补，他人可抢 |
| 抢单后主动放弃 | 状态 CANCELLED，名额立即回补 |
| 开始时间前 1 秒抢单 | 返回 NOT_STARTED |
| 截止时间后 1 秒抢单 | 返回 ALREADY_ENDED |
| 抢单过程中 Redis 宕机 | 降级为数据库锁，仍不超发 |
| 场次进行中追加名额 | 新增名额立即可抢，Redis 同步更新 |
| 长时间运行后校准 | Redis 计数与数据库 `used_quota` 一致 |

**推荐关系**

| 用例 | 预期结果 |
| --- | --- |
| 调整 B 的上级为其自身下级 D | 拒绝，提示会形成环路 |
| 调整含 20 个下级的节点 | 21 条记录 path/depth 全部正确更新 |
| 导入含环路的 Excel | 整批拒绝并定位到具体行 |
| 导入含未注册邮箱 | 该行跳过，输出未注册名单 |
| 关系调整后查历史报单 | 历史归属按快照不变，当前归属按新关系 |

**表单与提交**

| 用例 | 预期结果 |
| --- | --- |
| 绕过前端直接调接口提交非法数据 | 后端校验拦截 |
| 提交已存在的订单号 | 拦截并提示冲突单号 |
| 提交完全相同的图片 | MD5 命中，标记高危并按配置拦截 |

### 附录 C-1：需求确认纪要（V1.1，2026-08-10）

基于业务方对附录 C 的答复，以下决策**覆盖**原策划书中的"建议"口径，开发须按本纪要执行：

1. **关系建立方式变更**：由"导入星际未来 Excel"改为「注册填写邀请码绑定上级 + 后台客服人工核对」。不再依赖外部数据导出；关系调整通过后台人工指定上级，全程留痕（见 `RelationAdjustLog`）。
2. **去除短信验证（Q3）+ 加入注册人工审核（Q4）**：注册流程 = 填邮箱/手机号/密码/邀请码 → 状态 `PENDING` → 客服审核 → `ACTIVE` 方可登录使用。
3. **去除佣金 / 结算模块（Q9），新增"任务次数统计"**：本期仅记录"通过审核的任务次数"，结算完全走人工；导出与统计口径围绕"次数 + 提交明细"。
4. **提交截止改为"当日 18:00"（Q6）**：占位释放逻辑由"固定 60 分钟"改为"按任务截止时间（默认 18:00）计算"，到点未提交自动释放名额并通知。
5. **历史业绩按新关系重算（Q15）**：关系树调整后，团队业绩报表直接按当前树计算，**不做提交时快照**。报表口径以"当前关系"为准（业务方已确认接受追溯变动）。
6. **不做微信内集成（Q14）**：会员端为 H5 网页；驳回 / 审核结果通知走站内信 + 邮件。
7. **容量降级（Q11）**：会员 ≤1000、日单 ≤1000，原"千级并发抢单压测"仍保留原子扣减设计，但压测目标下调；单机 Docker 部署即可，不必上 K8s。
8. **部署方式（对应"腾讯云服务器搭建"诉求）**：采用容器化交付——本工作区完成开发自测后，产出 `docker-compose` 包（应用 + 独立 Postgres + 独立 Redis，**各自占用不与现有程序冲突的端口**）。在腾讯云服务器执行 `docker compose up -d` 即运行，与服务器上原有程序零耦合；回滚只需 `docker compose down`。**注意：服务器密码等敏感凭证请勿在对话中直接发送**，部署走容器化包交付最安全。
